# Showcase media (screenshots & videos of the product)

Neither the docs nor the marketing site used to *show* the product — it was
only ever described in text. Hand-captured media would rot, because the dash0
UI changes constantly, so the media we publish is **generated by driving the
real UI** and can be regenerated on demand.

## Where the pipeline lives

`web/dash0/showcase/` — a standalone Playwright project, deliberately *not*
part of the e2e suite (the e2e config pins `testDir: "./e2e"`, and showcase
files are named `*.showcase.ts`, so `bunx playwright test` and CI never pick
them up). Full details: [`web/dash0/showcase/README.md`](../../web/dash0/showcase/README.md).

Run it with:

```bash
# side-car test server, leaving a `make dev` loop on :4000 undisturbed
PORT=4321 SP_RUNMODE=test SP_DB_RESET=true ./solidping serve &
E2E_BASE_URL=http://localhost:4321/dash0/ make showcase
```

`make showcase` is **manual only** — there is no CI job and no scheduled
regeneration. That is a deliberate decision (spec 2026-08-07-02): CI
regeneration can come later, once the recorded flows have proven stable.

## What it produces

1. A Playwright recording (`video: "on"`, fixed 1280×800 viewport, light
   theme, `slowMo` pacing) of the canonical **create an HTTP check** flow:
   checks list → New check → HTTP type → name + URL → interval → regions →
   save → check detail page.
2. Named still frames captured during the same run.
3. Post-processing: dead frames at head/tail trimmed via ffmpeg
   `freezedetect`, then re-encoded to **AV1** (`libsvtav1`). Screen captures
   compress extremely well under AV1, so the committed assets stay tiny.

Pipeline scratch (`web/dash0/showcase/output/`, including the raw `.webm`
intermediates) is git-ignored. Only the post-processed assets are committed.

## Committed assets

| Path | What |
|---|---|
| `web/docs/static/showcase/create-http-check.mp4` | AV1 recording of the HTTP-check creation flow |
| `web/docs/static/showcase/01-checks-list.png` | Checks list |
| `web/docs/static/showcase/02-check-form-filled.png` | New-check form, filled in |
| `web/docs/static/showcase/03-check-detail.png` | Check detail page |

They ship inside the embedded `web/docs` build (no CDN, no extra infra) and are
served at `/docs/showcase/<file>` on every host — e.g.
<https://solidping.io/docs/showcase/create-http-check.mp4>.

Keep the catalog deliberately small: only assets that a published page actually
embeds. If it ever grows big enough to bloat the repo, moving to a CDN is a
follow-up spec.

## Where they are surfaced

  — the "Tour" page, reachable from the docs sidebar right after the
  introduction.

## Marketing hand-off — `www.solidping.io`

The marketing site is the **separate `solidping-website` repo**
(`../solidping-website`); it is not modified by this repo and was intentionally
left out of scope.

The expectation recorded here is that **www.solidping.io consumes the same
assets** listed above rather than growing its own hand-captured screenshots.
Two ways for that repo to pick them up, whichever the website maintainers
prefer:

- reference them at their served URLs under `https://solidping.io/docs/showcase/…`, or
- copy the committed files out of this repo at build time.

Either way, the source of truth is `web/docs/static/showcase/` here, and the
regeneration command is `make showcase` from the `solidping` repo root. When a
flow's UI changes, regenerate here first; the website picks up the new assets
from this same set.
