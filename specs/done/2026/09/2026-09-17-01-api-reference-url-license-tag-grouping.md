# The API reference lives at an ugly URL, renders an empty License block, and lists 275 endpoints as one flat wall

## Problem

The API reference is generated at build time by `docusaurus-plugin-openapi-docs`
from `server/internal/app/openapi/openapi.yaml`
([`web/docs/docusaurus.config.ts:95`](web/docs/docusaurus.config.ts:95)) into
`web/docs/docs/api/` (gitignored — [`web/docs/.gitignore:24`](web/docs/.gitignore:24)).
Three things are wrong with what it produces.

### 1. The landing page is at `/docs/api/solidping-api`, not `/docs/api`

The plugin names the intro page after the spec's `info.title` slug, so it lands at
`web/docs/docs/api/solidping-api.info.mdx` → `/docs/api/solidping-api`. `/docs/api`
itself is a bare sidebar category with no route behind it. Anyone linking to "the
API docs" has to paste a URL with the product name duplicated in it, and the
obvious guess (`/docs/api`) 404s.

### 2. The License section renders as a heading with nothing under it

`openapi.yaml:8-9` declares:

```yaml
  license:
    name: AGPL-3.0
```

`createLicense()` in the plugin only emits a link when `url` **or** `identifier`
is set — the `name` alone is never rendered on its own
(`web/docs/node_modules/docusaurus-plugin-openapi-docs/lib/markdown/createLicense.js:26-33`).
`identifier` is OpenAPI 3.1 only and this spec is `openapi: 3.0.0`, so today the
generated page ends with an empty `<h3>License</h3>` and no text. Confirmed in the
current `solidping-api.info.mdx`. The project is AGPL-3.0 (root `LICENSE`) and the
API reference says nothing about it.

### 3. Every endpoint is in one flat, unordered list

`sidebars.ts` is a single `{ type: "autogenerated", dirName: "." }`
([`web/docs/sidebars.ts:7`](web/docs/sidebars.ts:7)) and the plugin is configured
with **no** `sidebarOptions`, so all 275 `*.api.mdx` files sit flat in
`docs/api/` and the "API Reference" category lists them alphabetically by
filename — `accept-invite`, `acknowledge-incident`, `add-check-channel`, … There
is no way to see "everything about Checks" or "everything about SLOs".

The spec already carries the grouping information: **29 tags are declared** and
every one of the 276 operations is tagged (0 untagged). It is purely unused.

### 3b. Two tags are used but never declared — and they will silently vanish

`StatusPages` (38 operations) and `StatusUpdates` (5 operations) are set on
operations but are **missing from the top-level `tags:` block** of `openapi.yaml`
(which ends at `EmailSuppressions`, line 80-81).

This is inert today but becomes a data-loss bug the moment grouping is turned on:
`groupByTags()` builds its category list only from globally-declared tags that are
referenced (`lib/sidebars/index.js:72-79`), and the `UNTAGGED` fallback bucket
only catches operations with **no tags at all**
(`lib/sidebars/index.js:175-177`). Operations carrying an undeclared tag match
neither — **43 endpoints, including the entire public status-page API, would
disappear from the sidebar** with no warning in the build output.

## Proposal

All three are `web/docs` + `openapi.yaml` changes; no server code moves. The docs
site is embedded in the Go binary, so the acceptance check is the built site, not
just `docusaurus start`.

### Declare the missing tags first

Add `StatusPages` and `StatusUpdates` to the `tags:` block in
`server/internal/app/openapi/openapi.yaml`, with descriptions matching the style
of the existing 29. Do this **before** enabling grouping, and assert it: a test or
build-time check that every tag referenced by an operation is declared at the top
level is cheap and prevents this class of silent drop from coming back the next
time someone adds an endpoint. (`wiki/conventions/` is the place for the rule if a
check is not practical.)

### Give the license something to render

Add a `url` to `info.license` — `https://www.gnu.org/licenses/agpl-3.0.html`, or
the repo's own `LICENSE` — so the existing License block renders `AGPL-3.0` as a
link instead of an empty heading. Mention the license in `info.description` too if
it reads better there. Verify by grepping the regenerated
`docs/api/solidping-api.info.mdx` for the link, not by eye.

### Move the landing page to `/docs/api`

Set `slug: /api` on the generated info page so `/docs/api` resolves to it. The
file is generated, so the slug has to come from the generator: use the plugin's
`infoTemplate` (or `markdownGenerators.createInfoPageMD`) in
[`web/docs/docusaurus.config.ts:95-105`](web/docs/docusaurus.config.ts:95) rather
than post-editing the output. Pair it with
`sidebarOptions.categoryLinkSource: "info"` so the "API Reference" sidebar
category links to that page instead of being a dead expander.

`onBrokenLinks: "throw"` means any in-repo link to the old path fails the build
(there are none today — checked). Consider a client-side redirect from
`/docs/api/solidping-api` to `/docs/api` for external links; it needs
`@docusaurus/plugin-client-redirects`, which is not a dependency yet. Optional —
call it either way, don't leave it implicit.

### Group by tag

Add to the plugin config:

```ts
sidebarOptions: {
  groupPathsBy: "tag",
  categoryLinkSource: "info",   // or "tag" — see below
},
```

Two consequences to handle deliberately, both of which break things if ignored:

1. **The plugin emits `docs/api/sidebar.ts` and the generated pages stay flat** —
   `groupPathsBy: "tag"` does not create per-tag subdirectories. So the current
   `{ type: "autogenerated", dirName: "." }` in
   [`web/docs/sidebars.ts`](web/docs/sidebars.ts) would still list all 275 pages
   flat, *in addition to* the grouped ones. `sidebars.ts` has to stop
   autogenerating over `docs/api` and consume the generated slice instead.

2. **The generated `sidebar.ts` is gitignored and only exists after
   `gen-api-docs`.** `bun run build` runs `gen-api-docs` first, but
   `bun run start` and `bun run typecheck` do **not**
   ([`web/docs/package.json:7,19`](web/docs/package.json:7)) — so a naive
   `import apiSidebar from "./docs/api/sidebar"` breaks a fresh checkout's dev
   server and `tsc`. Pick one and make it work: add `gen-api-docs` to `start` and
   `typecheck`, commit a checked-in stub, or load the slice lazily with a fallback.
   Also add `!/docs/api/sidebar.ts` to `.gitignore` if the stub route is chosen.

Whether the category link source is `"tag"` (each tag category gets its own
description page from the tag's `description:`) or `"info"` is a judgement call —
`"tag"` gives every group a landing page built from descriptions that already
exist in the spec, which is the better outcome if it does not fight the `/docs/api`
slug above.

### Acceptance

- `cd web/docs && bun run build` is clean, and the built site has all **276**
  operations reachable from the sidebar — count them, do not spot-check. This is
  the check that catches the `StatusPages` drop.
- `/docs/api` serves the API landing page; `/docs/api/solidping-api` either
  redirects there or is intentionally gone (state which).
- The landing page shows `AGPL-3.0` as a link.
- The sidebar shows 31 tag groups (29 existing + the 2 newly declared), each with
  the operation count above.
- `bun run start` and `bun run typecheck` both work from a clean checkout with no
  `docs/api/` present.
- `make build` still embeds and serves the docs — check
  `http://localhost:4000/docs/api` on a real server, not just the Docusaurus dev
  server. The `/openapi` Swagger explorer is unaffected and should stay working.

## Implementation Plan

1. **`openapi.yaml` — declare the two missing tags and give the license a URL.**
   Add `StatusPages` and `StatusUpdates` to the top-level `tags:` block with
   descriptions in the style of the existing 29, and add
   `url: https://www.gnu.org/licenses/agpl-3.0.html` to `info.license`.

2. **Go regression test — `server/internal/app/openapi_tags_declared_test.go`.**
   Parse the embedded `openapi/openapi.yaml`, collect every tag referenced by an
   operation, and assert each one is declared at the top level. Assert the reverse
   too (no declared-but-unused tag, which would emit an empty tag page), and pin
   `info.license.url` so the License block cannot silently go empty again. Same
   "parse the YAML with a minimal struct" style as the existing
   `openapi_status_page_routes_test.go`.

3. **`web/docs/templates/openapi-info.mustache` — the info-page template.**
   A copy of the plugin's built-in info template with `slug: /api` added to the
   front matter, wired via `infoTemplate` in the plugin config. This is what moves
   the landing page from `/docs/api/solidping-api` to `/docs/api`; the file is
   generated, so the slug has to come from the generator.

4. **`web/docs/docusaurus.config.ts` — grouping + template wiring.**
   Add to the `docusaurus-plugin-openapi-docs` entry:
   `infoTemplate`, and `sidebarOptions: { groupPathsBy: "tag", categoryLinkSource: "tag" }`.
   Also add a `sidebarItemsGenerator` to the classic preset's docs options that
   drops the autogenerated "API Reference" category, so the 276 flat pages stop
   being listed twice.

5. **`web/docs/sidebars.ts` — consume the generated slice.**
   Import `./docs/api/sidebar` and append an explicit "API Reference" category
   whose `link` is the generated intro doc (taken from the slice's first item, not
   hardcoded) and whose `items` are the 31 tag categories.

6. **`web/docs/package.json` — make `start` and `typecheck` self-sufficient.**
   Both now run `gen-api-docs` first, so a clean checkout with no `docs/api/`
   still has `docs/api/sidebar.ts` when `sidebars.ts` imports it.

7. **QA.** `make build-backend lint-back test` for the Go side;
   `cd web/docs && bun run build` plus a programmatic count of the operations
   reachable from the built sidebar; a real side-car server on an alternate port
   serving `/docs/api` and `/openapi`.

### Judgement calls

- **`categoryLinkSource: "tag"`** (not `"info"`). Reading
  `lib/sidebars/index.js`, `"info"` drops the intro doc from the sidebar entirely
  (`if (rootIntroDoc && categoryLinkSource !== "info")`) and points *every* tag
  category at that same one page. `"tag"` gives each of the 31 groups its own
  landing page generated from the `description:` already in the spec, and keeps
  the intro doc at the top. It does not fight the `/docs/api` slug: the slug comes
  from `infoTemplate`, which is independent of the link source.
- **No redirect from `/docs/api/solidping-api`.** The old path is intentionally
  gone. It needs a new dependency (`@docusaurus/plugin-client-redirects`) to
  preserve a URL that nothing in the repo links to, that was never advertised, and
  that exists only because a generator defaulted to the spec title. Not worth a
  dependency in the binary-embedded docs build.
