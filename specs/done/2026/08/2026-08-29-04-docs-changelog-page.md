# The changelog never reaches users — surface it at /docs/changelog, cleaned up for reading

## Problem

Release-please maintains a rich `CHANGELOG.md` at the repo root — the entries are
already written as prose release notes (the release flow expands them in the
`chore(release)` PR before tagging) — but nothing user-facing ever shows it. A
self-hoster or SaaS user has to dig through GitHub to learn what changed between
releases, even though the docs site is embedded in the very binary they run.

The raw file is also not directly presentable:

- **Form.** Every bullet ends in link clutter —
  `([#282](…/issues/282)) ([289478e](…/commit/289478e…))`, sometimes several
  pairs on one line — and version headings are
  `## [0.20.0](…/compare/v0.19.1...v0.20.0) (2026-08-29)`. Readable on GitHub,
  noisy as a docs page.
- **Noise.** `fix(deps)` bumps (e.g. "update github.com/dop251/goja digest to
  8f1c069") are changelog-accurate but meaningless to a user reading "what's
  new".
- **Scopes.** Section bullets lead with internal scope slugs (`**dash0:**`,
  `**status pages:**`, `**sftp:**`) that don't all read as product-facing names.
- **MDX hazard.** Docusaurus 3 compiles `.md` as MDX by default; a changelog is
  exactly where a stray `<name>` or `{` in prose would break the docs build.

## Proposal

### 1. Build-time generated page (single source of truth stays at the root)

Follow the existing generated-API-reference pattern
([docusaurus.config.ts:12](web/docs/docusaurus.config.ts), gitignore carve-out in
[web/docs/.gitignore](web/docs/.gitignore)):

- Add a small script, e.g. `web/docs/scripts/gen-changelog.ts`, that reads the
  root [CHANGELOG.md](CHANGELOG.md), transforms it (below), and writes
  `web/docs/docs/changelog.md`.
- Run it from the `build` script in [web/docs/package.json](web/docs/package.json)
  (before `docusaurus build`, alongside `gen-api-docs`) so `make build-docs`
  ([Makefile:144](Makefile)) and CI's Docs Build pick it up with zero drift —
  whatever release-please last wrote is what ships. Also run it from `start` so
  `bun run start` previews it.
- Gitignore `/docs/changelog.md` in `web/docs/.gitignore`, same as `/docs/api/*`.
- Frontmatter injected by the script: `title: Changelog`, `sidebar_position` so
  it lands **last** in the autogenerated sidebar
  ([sidebars.ts](web/docs/sidebars.ts)), and `format: md` so the page compiles
  as CommonMark, immune to MDX-illegal characters in entry prose.

Free consequences worth asserting in tests: the page is embedded in the binary,
so `/docs/changelog` on any instance shows the changelog *up to that instance's
release*; `docusaurus-plugin-llms`
([docusaurus.config.ts:79](web/docs/docusaurus.config.ts)) folds it into
`llms.txt`/`llms-full.txt` automatically.

### 2. Transform for form — make it read as release notes

The script rewrites, deterministically:

- **Version headings** → `## 0.20.0 — 2026-08-29`, keeping the compare link but
  demoted to a small trailing link (e.g. `([diff](…/compare/v0.19.1...v0.20.0))`)
  rather than wrapping the heading text. Headings keep stable anchors
  (`/docs/changelog#0200`) for linking from announcements.
- **Reference clutter** → per bullet, keep **one** PR link (`#282`) and drop the
  raw commit-hash links; multiple `([#N]) ([hash])` pairs collapse to the
  distinct PR numbers.
- **Scope labels** → map known scopes to product-facing names via a small
  lookup (`dash0` → Dashboard, `status pages` → Status pages, `sftp` → SFTP
  checks, `api` → API, `auth` → Authentication, …); unknown scopes pass through
  unchanged rather than failing.
- **Noise filtering** → drop `deps` bullets entirely from the docs page (they
  stay in the root CHANGELOG.md); if that leaves a `### Bug Fixes` (or other)
  section empty, drop the section; if that leaves a release with no entries,
  keep the version heading with a single "Maintenance release." line.
- **Robustness** → the transform must be tolerant: any line it doesn't
  recognize passes through verbatim. It must never fail the docs build on an
  unexpected changelog shape.

Unit-test the transform with `bun test ./src` (the docs package already wires
`test:unit`): fixtures covering a multi-pair-link bullet, a deps-only release,
an unknown scope, and MDX-hostile characters surviving into output.

### 3. Convention for content — entries written for this page

Codify what the release flow already does informally, so future entries render
well here by construction. Add `wiki/conventions/changelog.md` (wiki, not the
docs site) stating:

- Entries are **user-facing prose**: what changed for the person using the
  product, not internal mechanics; internal-only refactors stay out or under a
  scope the filter drops.
- Scopes come from the mapping table in the transform script — adding a new
  scope means adding its display name there.
- The `chore(release)` PR pass (the existing expand-the-changelog step) is the
  moment to check the rendered page: `bun run start` in `web/docs` shows it.

Reference the new convention from the release notes in `CLAUDE.md` only if a
one-line pointer fits naturally; the wiki page is the canonical text.

## Out of scope

- Splitting the page per major version (revisit if the single page grows
  unwieldy).
- Rewriting historical entries in the root CHANGELOG.md — the transform must
  make the existing history presentable as-is.
- Any change to release-please configuration or the release flow itself.
