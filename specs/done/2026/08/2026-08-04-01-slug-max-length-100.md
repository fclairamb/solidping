# Entity slug max length is inconsistent (20/40/50) — extend to 100 chars

## Problem

Resource slugs (checks, check groups, status pages, severities) are capped at
inconsistent, fairly short lengths, and the caps have drifted between the
regexes, the error messages, and the frontend:

- **Checks**: `server/internal/handlers/checks/service.go:74` allows
  `^[a-z][a-z0-9-]{2,49}$` (3–50 chars), but the comment above it still says
  "2-19" and the three handler error messages
  (`server/internal/handlers/checks/handler.go:712`, `:775`, `:875`) still tell
  the user "Slug must … be 3-20 characters".
- **Check groups**: `server/internal/handlers/checkgroups/service.go:19` —
  `{2,39}` (3–40).
- **Status pages**: `server/internal/handlers/statuspages/service.go:26` —
  `{2,39}` (3–40).
- **Severities**: `server/internal/handlers/severities/service.go:41` —
  `{2,39}` (3–40); error message at
  `server/internal/handlers/severities/handler.go:109` says "3-40".
- **Frontend** mirrors the same drift:
  `web/dash0/src/lib/utils.ts:14` (`slugify()` truncates at 40),
  `web/dash0/src/components/shared/check-form.tsx:299` (`{2,49}`),
  `web/dash0/src/components/shared/status-page-form.tsx:119` (`pattern="^[a-z][a-z0-9-]{2,39}$"`),
  `web/dash0/src/routes/orgs/$org/checks.index.tsx:123` and
  `web/dash0/src/routes/orgs/$org/check-groups.$uid.edit.tsx:161` (`{2,39}`).

Long descriptive names ("production-eu-west-payments-gateway-health…") get
rejected or silently truncated by `slugify()` at 40 chars.

**Correction (found during implementation):** the claim below that "the limit
is purely regex-side" is wrong. Slug DB columns are TEXT (no `varchar(N)`
anywhere in migrations) — but `check_groups`/`checks`/`status_pages`/
`status_page_sections` carry DB-level length **CHECK constraints** that
mirror the old regex bounds: sqlite `001_v0_1_0.up.sql` has
`length(slug) <= 40` (check_groups), `<= 50` (checks), `<= 40` (status_pages,
status_page_sections); postgres `001_v0_1_0.up.sql` has the equivalent
`slug ~ '...{2,39}$'` / `{2,49}$'` regex CHECK constraints. Without widening
these, a 90-char slug would pass the widened Go regex and then be rejected by
the database — a 500 instead of a clean validation error, worse than the
status quo. A migration **is** required; see Proposal item 5.

## Proposal

Raise the max length of **entity slugs** to **100 chars** (min stays 3, format
stays `^[a-z][a-z0-9-]{2,99}$`), consistently across backend and frontend:

1. **Backend regexes** → `{2,99}`:
   - `server/internal/handlers/checks/service.go:74` (also fix the stale
     "2-19" comment),
   - `server/internal/handlers/checkgroups/service.go:19`,
   - `server/internal/handlers/statuspages/service.go:26`,
   - `server/internal/handlers/severities/service.go:41`.
2. **Backend error messages** → say "3-100 characters":
   - `server/internal/handlers/checks/handler.go:712`, `:775`, `:875`
     (currently claim 3-20 — already wrong today),
   - `server/internal/handlers/severities/handler.go:109`.
3. **Frontend** (dash0):
   - `web/dash0/src/lib/utils.ts:14` — `slugify()` `.slice(0, 40)` →
     `.slice(0, 100)`,
   - `web/dash0/src/components/shared/check-form.tsx:299` → `{2,99}` (and its
     validation message),
   - `web/dash0/src/components/shared/status-page-form.tsx:119` → `{2,99}`
     (and any adjacent help text),
   - `web/dash0/src/routes/orgs/$org/checks.index.tsx:119-123` and
     `web/dash0/src/routes/orgs/$org/check-groups.$uid.edit.tsx:157-161` →
     `{2,99}` (update the "3-40 chars" comments).
4. **Tests**: update existing slug-validation tests (e.g.
   `server/internal/handlers/checkgroups/slug_test.go`, checks/severities
   service tests) with boundary cases: 100 chars accepted, 101 rejected, 3
   accepted, 2 rejected.
5. **Migration required** (see the "Correction" note in Problem above):
   widen the DB-level length CHECK constraints on `check_groups`, `checks`,
   `status_pages`, and `status_page_sections` from 40/50 to 100 chars, in
   both `server/internal/db/sqlite/migrations/` and
   `server/internal/db/postgres/migrations/`. `severities` has no such
   constraint and needs no migration change. Postgres constraints are a
   simple `alter table ... drop constraint ... / add constraint ...` swap.
   SQLite has no `ALTER COLUMN`/`DROP CONSTRAINT`, so each table must be
   rebuilt with the `*_new` create/copy/drop/rename pattern already
   established in this repo (see `005_v0_4_0.up.sql`) — including disabling
   `foreign_keys` for the duration (these tables are FK-referenced parents;
   with enforcement on, `DROP TABLE` fires child `ON DELETE` actions against
   the live child rows before the rebuilt table is swapped back in) and using
   explicit column lists in the `INSERT ... SELECT` (never `select *`, which
   is positional and silently scrambles data on any column drift).

**Out of scope** (deliberately unchanged):
- **Org slugs** — `server/internal/orgslug/orgslug.go` and
  `server/internal/handlers/auth/service.go:2623` keep 3–20: the org slug is a
  URL path segment and a JWT claim, and widening it has auth/routing blast
  radius.
- **Private region slugs** — `server/internal/regions/regions.go:59` keeps
  2–30.
- **Auto-generation caps** — `checksleep` `slugMaxLen = 50`
  (`server/internal/checkers/checksleep/checker.go:24`), discovery's
  `maxSlugLen = 50` (`server/internal/discovery/suggest.go:185`), and the
  worker's hostname-derived cap (`server/internal/checkworker/worker.go:330`)
  generate slugs that remain valid under the new max; raising them is not
  required.
