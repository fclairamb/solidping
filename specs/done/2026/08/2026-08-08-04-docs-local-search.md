# Docs site has no search — add offline full-text search with @easyops-cn/docusaurus-search-local

## Problem

The Docusaurus docs site (`web/docs/`, served embedded at `/docs` on every
host) has no search at all. With ~30 hand-written pages plus the generated
OpenAPI reference, finding a config key, an endpoint, or a migration guide
means clicking through the sidebar.

The usual Docusaurus answer — Algolia DocSearch — is wrong for this
architecture: the docs are embedded in the Go binary
(`server/internal/app/server.go:151`, `//go:embed all:docsres`) precisely so
they work on self-hosted and air-gapped installs with no extra infra. A hosted
search service would only index the public `docs.solidping.io` and would make
every self-hosted deployment call out to Algolia. Self-hosted search servers
(Typesense, Meilisearch) add the infra the embedded design avoids.

## Proposal

Use **`@easyops-cn/docusaurus-search-local`**: it builds a lunr index at build
time as static assets in the Docusaurus build output, so the index ships
inside the embedded FS with zero server-side changes and works fully offline.
The index loads lazily on first focus of the search box, so initial page loads
are unaffected.

1. **Add the dependency** in `web/docs/` (bun is the package manager:
   `bun add @easyops-cn/docusaurus-search-local`).

2. **Register the theme** in `web/docs/docusaurus.config.ts`:

   ```ts
   themes: [
     [
       require.resolve("@easyops-cn/docusaurus-search-local"),
       {
         hashed: true,            // long-term-cacheable index filenames
         docsRouteBasePath: "/",  // docs are served at the site root (routeBasePath: "/")
         indexBlog: false,        // blog is disabled
         highlightSearchTermsOnTargetPage: true,
       },
     ],
   ],
   ```

   The plugin respects `baseUrl: "/docs/"` out of the box, so search works
   identically on `solidping.io/docs` and `docs.solidping.io`.

3. **Index scope**:
   - **Include the OpenAPI reference pages** (`/api/...`, generated by
     `docusaurus-plugin-openapi-docs`) — searching for an endpoint name is a
     primary use case. They are regular docs routes, so they are indexed by
     default; nothing to do.
   - **Verify the `docusaurus-plugin-llms` outputs are NOT indexed.**
     `llms.txt` / `llms-full.txt` and the per-page markdown mirrors are static
     files in the build output, not Docusaurus routes, so the search plugin
     should ignore them — but verify by inspecting the generated index (no
     duplicate hits for the same page). If they do leak in, exclude them via
     the plugin's ignore options.

4. **Verify the embedded pipeline end to end**: `make build-docs copy-docs`
   (see Makefile), then confirm the search index files land in
   `server/internal/app/docsres/` and the search box returns results when
   served from the Go binary at `/docs`. Watch index size — if the OpenAPI
   pages balloon it (hundreds of KB gzipped), reconsider their inclusion, but
   default to keeping them.

5. **Test**: add a lightweight Go test alongside
   `server/internal/app/docs_test.go` asserting the embedded docs FS contains
   the search index assets (glob for the hashed `search-index*.json` /
   lunr chunk names), so a future build-pipeline change that silently drops
   search fails CI.

No Go routing changes are expected: the index files are plain static assets
served by the existing docs file server.
