# Per-org deported agents over WebSocket, with asymmetrically sealed credentials

## Problem

Customers want to monitor infrastructure that is not reachable from SolidPing's
cloud workers (private networks, on-prem datacenters). They need an **org-scoped
deported agent** they can run inside their network that:

- connects **outbound-only over WebSocket** (no inbound ports, firewall-friendly),
- enrolls with a **one-shot token**, generates its own keypair, and sends only the
  public part to the server,
- claims check jobs (reserving them) and submits results (marking them processed),
  exactly like the internal worker loop,
- has **no database** and can do **nothing but checks** — the server must enforce
  this, not trust the agent,
- and for whose checks credentials are **not recoverable by the server alone**:
  credentials destined only for an org-private region must not sit in the DB under
  the existing symmetric envelope (or worse, plaintext) — they must be sealed
  asymmetrically so only the region's agents can decrypt them.

Current state, and why it falls short:

- The production worker is **in-process, direct-to-Postgres**: `CheckWorker`
  (`server/internal/checkworker/worker.go`) is started when
  `Config.ShouldRunChecks()` (`server/internal/config/config.go:301`) and talks
  straight to `checkjobsvc`. "Distributed" today = several server replicas sharing
  one Postgres. A deported agent cannot work this way (no DB access).
- A remote-worker **HTTP API exists but has no production client** and weak auth:
  routes wired at `server/internal/app/server.go:773-777`
  (`/api/v1/workers/{register,heartbeat,claim-jobs,submit-result}`),
  `Register` is unauthenticated (`server/internal/handlers/workers/service.go:107`),
  worker tokens are plaintext `spw_` strings stored and matched verbatim
  (`service.go:350`, `ValidateToken` `service.go:66`). The `WorkerBackend`
  abstraction (`server/internal/checkworker/backend/backend.go:29`, with
  `DirectBackend` and a test-only `HTTPBackend`) exists but `CheckWorker` does not
  use it.
- Credentials at rest use **symmetric envelope encryption only** (per-org AES-256-GCM
  DEK wrapped by an out-of-band KEK, `server/internal/crypto/credentials/service.go`)
  and are **decrypted server-side before dispatch**
  (`server/internal/handlers/workers/service.go:181`). There is no asymmetric
  crypto anywhere in the codebase.
- Regions are global-only (`server/internal/regions/regions.go`); worker↔job
  matching is prefix-based (`MatchesRegion`, `regions.go:190`), which is a routing
  mechanism, not a security boundary.

## Decisions (settled in design discussion — do not re-litigate)

1. **Agent = the standard container/binary in agent mode** (`SP_NODE_ROLE=agent`).
   No separate slim binary. Agent mode must skip DB init and migrations entirely.
2. **WebSocket is the only agent transport.** The existing HTTP worker API is
   **removed entirely** (routes, `HTTPBackend`, `spw_` token generation/validation,
   the `workers.token` column). The claim/submit *service logic* is kept and reused
   by the WS handler.
3. **Multiple agents per private region (HA) from day one** → credentials are
   sealed to the **region** with multi-recipient encryption, not to a single agent.
4. **Mixed regions allowed**: a credential-bearing check may target both a private
   region and cloud regions. In that case secrets are **dual-stored** (existing
   org-DEK envelope for cloud dispatch + sealed blob for agents). A check targeting
   **only** private regions stores secrets **sealed-only** — the server cannot
   decrypt them after write.
5. **Server-side sealing first** (credentials arrive over TLS via API/dashboard, the
   server seals them at write time) so scripts/automation keep working with plain
   API calls. Client-side (browser) sealing is a later, separate spec.
6. Agent key persistence: **file or environment variables** — both supported.
7. Two keypairs, generated by the agent: **Ed25519 for identity** (auth
   signatures), **X25519 for credential encryption**. Never reuse one raw key for
   both purposes.

## Proposal

### Phase 1 — WS agent, enrollment, private regions

**Data model** (new migration):

- `agents`: `uid`, `org_uid`, `region` (fully-qualified private-region slug),
  `name`, `ed25519_public_key`, `x25519_public_key`, `fingerprint` (short hash of
  the Ed25519 key, shown in UI/logs), `status` (`active`/`revoked`),
  `last_seen_at`, `enrolled_at`, `revoked_at`.
- `agent_enrollment_tokens`: `uid`, `org_uid`, `region`, `token_hash`
  (SHA-256 of the random secret — never store the token itself), `expires_at`
  (default 24h), `used_at`, `used_by_agent_uid`, `created_by_user_uid`. Token
  format `spe_<32 random bytes hex>`, displayed exactly once at creation.
- **Private regions**: org-scoped region definitions (slug, name, emoji) stored as
  an org parameter (`custom_regions`), managed via the org API/dashboard. The
  stored job-region string is namespaced with a reserved character, e.g.
  `@<org-slug>/<region-slug>`, and cloud-worker region validation
  (`ValidateWorkerRegion`, `regions.go:168`, plus `SP_NODE_REGION` parsing) must
  reject `@` — this makes it structurally impossible for a cloud worker's
  prefix match (`MatchesRegion`, `regions.go:190`) to ever claim a private-region
  job. Check region pickers and `ResolveRegionsForCheck` (`regions.go:127`)
  include the org's private regions; `reconcileCheckJobs` already materializes one
  `check_jobs` row per region string and needs no schema change.

**Enrollment flow** (first connection):

1. Admin creates a private region, then mints an enrollment token bound to
   (org, region).
2. Agent starts with `SP_AGENT_SERVER_URL` + `SP_AGENT_ENROLLMENT_TOKEN`, generates
   both keypairs, connects to `GET /api/v1/agent/ws` with
   `Authorization: Bearer spe_…` **before the upgrade** (proper HTTP 401/403 on
   failure, same pattern as the dashboard WS handshake in
   `server/internal/handlers/realtimews/handshake.go`).
3. First message after upgrade: `enroll` with both public keys and a name (default:
   hostname). Server validates the token (hash lookup, unexpired, unused), creates
   the agent row **atomically with marking the token used** (single-use under
   concurrency), and replies with the agent UID + fingerprint. The connection then
   proceeds directly to normal operation.
4. Agent persists its keys: to `SP_AGENT_KEYS_FILE` (default e.g.
   `/data/agent-keys.json`) when writable, and always logs that env-based
   operation is possible by setting `SP_AGENT_KEYS` (the same JSON, base64) —
   supporting both file-based and env-only (k8s secret) deployments.

**Reconnect auth** (every subsequent connection): signed headers before the
upgrade — `X-SP-Agent-Uid`, `X-SP-Timestamp`, `X-SP-Nonce`, `X-SP-Signature`
(Ed25519 over `method|path|timestamp|nonce`). Accept ±5 min clock skew; reject
replayed nonces within the window. No bearer token exists anywhere — the DB never
holds a usable agent credential, only public keys. Revoked agents get 403 and any
live connection is closed.

**WS protocol**: versioned JSON text frames with correlation IDs (follow the
`realtimews` message conventions, `coder/websocket` library). Messages:

- server → `hello` (protocol version, server time, agent identity echo)
- agent → `claim {maxJobs}` / server → `jobs {jobs[]}` — jobs carry public config
  plus (phase 2) the sealed credential blob
- agent → `result {jobUid, …}` / server → `ack` — server-side processing identical
  to the existing `SubmitResult` path (`handlers/workers/service.go:254`):
  lease-ownership guard, result row write, **incident processing stays
  server-side**
- server → `jobs-available` hint, wired to the existing notifier events (the
  express path for newly created checks) so the agent claims immediately instead
  of polling
- keepalive pings; `last_seen_at` updated periodically.

**Execution engine reuse**: finish the `WorkerBackend` refactor — make
`CheckWorker` consume `WorkerBackend` (`backend/backend.go:29`) so the lease/lane
loop, budgets, and express path run identically everywhere. `DirectBackend`
in-process on the server (unchanged behavior); new `WSBackend` in agent mode.
Extend the interface as needed for push hints. Lease semantics in
`checkjobsvc` are untouched — lease expiry already handles an agent dying mid-job,
and `lease_starts` crash-loop detection keeps working.

**Server-side enforcement (checks-only, untrusted agent)**:

- Agent job claims are **hard-scoped**: `org_uid` = agent's org AND `region` =
  agent's exact bound region. No prefix matching on the agent path.
- Validate result payloads (size caps, sane fields); everything an agent sends is
  untrusted customer input.
- Rate-limit claims/results per org using the existing `maxChecksPerMinute`
  entitlement.
- The WS surface is exactly the messages above — no config reads, no other
  entities, no org data.

**Removal** (per decision 2): delete the `/workers/*` route group
(`server.go:773-777`), the `handlers/workers` HTTP handler layer and token code
(`Register`/`ValidateToken`/`generateWorkerToken`), `backend/http.go`, and drop
`workers.token`. Keep the `workers` table + `RegisterOrUpdateWorker` used by the
in-process worker for heartbeat/visibility.

**Dashboard** (follow `design-reference.tsx` conventions, mobile-usable, E2E):

- Org settings → **Private locations** page: create/delete private regions; mint
  enrollment token (shown once); agents list (name, region, fingerprint, last
  seen, status) with revoke (destructive red, `Trash2`).
- Check form region picker includes the org's private regions.

**Docs**: a `web/docs` page — running the agent (docker run / k8s example, env
vars, enrollment, key persistence).

### Phase 2 — region-sealed credentials

- **Sealing primitive**: `filippo.io/age` X25519 recipients (audited, native Go,
  multi-recipient built in; the official TypeScript implementation exists for the
  later client-side phase). The sealed blob = age-encrypt of the JSON object of
  secret fields, recipients = the X25519 keys of all **active** agents of the
  check's private region(s) at write time. Stored in the existing
  `config_private` column with a new envelope version/alg marker alongside the
  current v1 symmetric envelope (`crypto/credentials/service.go`); recipient
  fingerprints are recorded in the envelope. `SecretFields()`/`SplitConfig`
  stay the single source of what is secret.
- **Write path** (check create/PATCH): plaintext secrets arrive over TLS (API or
  dashboard). Targeting private region(s) only → seal-only, **no org-DEK copy**;
  mixed private+cloud → dual-store (org-DEK envelope for cloud dispatch + sealed
  blob for agents). PATCH semantics for sealed-only checks: secrets provided →
  new blob replaces old; secrets absent → old blob kept **as-is** (the server
  cannot partially merge what it cannot read — document this).
- **Dispatch**: private-region jobs ship the sealed blob verbatim (the server-side
  decrypt at dispatch, today in `handlers/workers/service.go:181`, must NOT happen
  on the agent path). The agent unseals with its X25519 key, merges via the
  existing `MergeConfig`, executes, and keeps plaintext in memory only.
- **New agent joins a region**: earlier sealed-only blobs don't include it.
  Mixed-mode checks are re-sealed automatically (server can decrypt via org DEK).
  Sealed-only checks are flagged **needs re-seal** (computed from recipient
  fingerprints vs active agents), surfaced in the API and dashboard; the agent
  reports a decrypt failure as a clear job error ("credentials not sealed for this
  agent — re-save the check's credentials"). Fix = re-save credentials.
- **Revocation**: re-seal excluding the revoked agent where the server can (mixed
  mode); flag sealed-only checks for re-seal. Docs must state the honest caveat: a
  revoked agent already saw past credentials — rotate them.

### Out of scope / follow-ups (separate specs)

- **Client-side (browser) sealing** with fingerprint-verification UX — and its
  restriction that such checks may only target private regions.
- **Peer re-wrap**: asking an online agent to add a new recipient to a sealed-only
  blob so credentials never need re-entry.
- Agent auto-update / version reporting beyond a simple version field in `hello`.

## Testing

- Unit: enrollment token lifecycle (single-use race, expiry), signature auth
  (skew, replay, revoked), seal/unseal round-trip, multi-recipient, envelope
  versioning next to v1 symmetric.
- Integration (in-process WS against `httptest`, both PG and SQLite where
  applicable): enroll → claim → execute → result → incident; reconnect with
  signed headers; second agent HA claim; agent death → lease expiry → re-claim;
  region scoping (agent cannot claim other orgs/regions; cloud worker never
  matches `@…` regions); mixed-region dual-store; needs-re-seal flag; revocation.
- Playwright E2E for the Private locations page and the check-form region picker.
- Regression: existing in-process worker behavior unchanged after the
  `WorkerBackend` refactor; existing credential envelope (v1) untouched for
  cloud-only checks.

## Implementation Plan

This is a large two-phase spec. It is built in **green, independently-committable
increments**, in dependency order, so the tree compiles and tests pass at every
commit. Steps are grouped; each group is a commit (or a few).

### Group 1 — Private regions + cloud/private security boundary (self-contained)
- `regions.go`: add `PrivateRegionPrefix = "@"`, `IsPrivateRegion(s)`,
  `PrivateRegionSlug(orgSlug, regionSlug)`, `ParsePrivateRegion(s) (org, region, ok)`.
- `ValidateWorkerRegion` rejects any region containing `@` (a cloud/in-process
  worker can never bind a private region). The DB `workers.region` check
  constraint (`^[a-z][a-z0-9-]{3,20}$`) already forbids `@`; this makes the app
  layer reject it explicitly too.
- `MatchesRegion(workerRegion, jobRegion)`: when `jobRegion` is private, return
  true **only** on exact equality (never prefix) — structurally a cloud worker's
  prefix match can never claim an `@…` job.
- Org-scoped private regions stored as org parameter `custom_regions` (list of
  `{slug,emoji,name}`): `GetOrgCustomRegions(orgUID)`, `SetOrgCustomRegions`.
  Fully-qualified stored job region = `@<org-slug>/<region-slug>`.
- `handlers/regions` + org API/dashboard: list/create/delete private regions;
  `ListOrgRegions` includes private regions (flagged `private:true`, fully-qualified
  slug) so the check-form picker shows them.
- Tests: `@` rejection, `MatchesRegion` never prefix-matches `@…`, private-region
  parse/build, custom-region param round-trip.

### Group 2 — Region-sealed credentials primitive (`filippo.io/age`, self-contained)
- New `credentials/sealing.go`: `SealForRecipients(recipients []string, secrets
  map[string]any) (string, error)` → age-encrypt JSON of secrets to X25519
  recipients, wrapped in a **v2 envelope** `{v:2, alg:"age-x25519",
  fingerprints:[...], ct:<base64 armored/binary>}` alongside the v1 symmetric
  envelope. `UnsealWithIdentity(ageIdentity, envelope)`. `SealedRecipientFingerprints(envelope)`,
  `EnvelopeVersion(envelope)`, `RecipientFingerprint(recipient)`, `NeedsReseal(envelope,
  activeFingerprints)`.
- `GenerateAgentKeys()` helper (agent-side): Ed25519 (identity) + age X25519
  (encryption); returns public strings + a JSON persistence blob.
- Tests: seal/unseal round-trip, multi-recipient (N identities each decrypt),
  v1/v2 envelope discrimination, needs-reseal, tamper rejection.

### Group 3 — Agent identity crypto: enrollment tokens + Ed25519 reconnect auth
- New `agents` package: `spe_<hex>` enrollment-token mint + SHA-256 hashing;
  Ed25519 `SignChallenge`/`VerifySignature` over `method|path|timestamp|nonce`;
  clock-skew (±5m) + in-memory nonce replay cache; fingerprint of Ed25519 key.
- Tests: token hash/verify, signature verify, skew reject, replay reject.

### Group 4 — Data model (migration + models + registration)
- Migration `007_v0_6_0.{up,down}.sql` in **both** postgres & sqlite dirs:
  `create table agents`, `create table agent_enrollment_tokens`, and
  `alter table workers drop column token`.
- `models/agent.go`: `Agent`, `AgentEnrollmentToken` structs (bun tags matching
  conventions). Register in postgres + sqlite model registration lists.
- Remove `Token` from `models.Worker`.
- db.Service methods for agents/tokens (create token atomically-consume, create
  agent, get by uid, update last_seen, revoke, list, active X25519 recipients per
  region).

### Group 5 — Agent service (server side)
- `handlers/agents` service+handler: mint token (admin), list agents, revoke
  (destructive), needs-reseal listing. Atomic single-use enroll (mark token used
  + insert agent in one tx).

### Group 6 — WorkerBackend refactor
- Make `CheckWorker` consume `backend.WorkerBackend` (DirectBackend unchanged
  behavior in-process). Add push-hint extension as needed. Keep lease semantics
  untouched.

### Group 7 — Agent WS transport + agent mode
- WS handler `GET /api/v1/agent/ws` mirroring `realtimews` (auth-before-upgrade;
  enrollment bearer on first connect, signed headers on reconnect). Messages:
  `hello`/`enroll`/`enrolled`/`claim`/`jobs`/`result`/`ack`/`jobs-available`.
  Reuse `workers.Service` claim/submit; hard-scope claims to agent org+exact
  region; skip server-side decrypt on agent path (ship sealed blob verbatim).
- `SP_NODE_ROLE=agent`: skip DB init/migrations; run a `WSBackend` agent loop that
  enrolls, persists keys (`SP_AGENT_KEYS_FILE` / `SP_AGENT_KEYS`), claims, unseals,
  executes, submits.

### Group 8 — Phase 2 write/dispatch path
- `checks.applyEncryption`: when a check targets private region(s), seal secrets to
  the region's active agent recipients (seal-only for private-only; dual-store for
  mixed). PATCH keeps old sealed blob when secrets absent. Dispatch on agent path
  ships the sealed blob; re-seal on membership change where server can; flag
  needs-re-seal otherwise.

### Group 9 — Removal of HTTP worker API
- Delete `/workers/*` routes, `workers/handler.go`, `ValidateToken`/`Register`/
  `generateWorkerToken`, `backend/http.go`. Keep `workers.Service` claim/submit,
  `RegisterOrUpdateWorker`, workers table.

### Group 10 — Dashboard + docs + E2E
- dash0 **Private locations** page (create/delete regions, mint token shown once,
  agents list with revoke `Trash2` destructive); region picker includes private
  regions. `web/docs` agent page. Playwright E2E for the page.

**Honesty note:** given the scope, groups are landed in green order; any group not
reached is reported as not-yet-implemented in the final report rather than left
half-built.

**Status: all 10 groups implemented.** Verified end-to-end with the real binary:
a server in test mode + `SP_NODE_ROLE=agent` process enrolled with a one-shot
token, persisted its keys, reconnected with signed headers, claimed a
private-region check hard-scoped to `@test/dc1`, executed it, and submitted the
result (check went UP server-side). Known intentional deltas from the plan:

- Mixed dual-store keeps both blobs on the `checks` row in two columns
  (`config_private` + new `config_sealed`) rather than one packed envelope; job
  rows carry both and the WS dispatch strips `config_private` structurally.
- A private-only check created **before any agent enrolled** cannot be sealed
  (zero recipients); its secrets stay under the v1 envelope with
  `needsReseal: true` surfaced until re-saved — the spec leaves this case
  undefined, and dropping the secrets outright would break the check.
- Agent-path jobs do not update cost/delay EWMAs or lanes (the server's plain
  `ReleaseLease` re-anchors on ack); cost-aware ordering still applies via
  `effective_scheduled_at` at claim time.
- Nonce replay protection is per-instance (in-memory cache), as is the hint
  fan-out; multi-replica agent WS termination would need a shared cache —
  noted for the ops docs, not needed for the single-binary deployment today.
