# Confine `${env:}` secret references to an operator allowlist, at save time and at resolve time

## Problem
Found by the security scan of 2026-10-12 (finding N1). **Critical**, triggerable by any role ≥ `user` — on a SaaS instance with open signup, anyone who registers, since any authenticated user can create their own org (`server/internal/app/server.go:915-918`).

A check config string may carry `${env:NAME}`, and at execution the worker resolves it against **this process's entire environment** with no allowlist: `secretref.LookupEnv` is a bare `os.LookupEnv` (`server/internal/secretref/resolvers.go:81-88`). For the default in-process worker that process is the API server, so its secrets are in scope.

- The worker resolves on claim: `materializeConfig` → `secretref.ExecutionResolverWith` (`server/internal/checkworker/worker.go:909-951`, resolver wiring at `:944-945`). `ExecutionResolver` (`resolvers.go:137-156`) resolves `SchemeEnv` via `LookupEnv`.
- Same `ExecutionResolver` runs on the two bastion/tunnel paths: `checkworker/backend/ws_tunnel.go:50` and `integrations/sshtunnel/sshtunnel.go:249`.
- A plain `POST/PATCH /orgs/:org/checks` stores the reference verbatim: no write-path check rejects an `${env:}` whose name is off-limits (the create/update/clone/PUT paths run `firstConfigValidationError` — `plan.go:227`, `:543`, `service.go:5423` — which never inspects `env:` references).
- The only `${env:}` handling on the write path is in import/apply, and it is the *opposite* of a guard: `secretRefFindings` resolves every reference with `secretref.DocumentResolver` (`apply.go:319-350`), which resolves `SchemeEnv` through `LookupEnv` on the API process (`resolvers.go:96-111`). So import/apply (and the document-validate endpoint, `validate_document_endpoint.go:142`) tell the caller whether a server env var *exists* — a 400-vs-200 / finding-vs-no-finding oracle — and, worse, treat a resolvable server secret as a valid reference to store.

**Impact.** A `user`-role member creates an HTTP check whose `url` or a header value embeds `${env:SP_AUTH_JWT_SECRET}` / `${env:SP_DB_URL}` / `${env:SP_ENCRYPTION_MASTER_KEY}`; on the next run the worker sends the resolved value to the attacker's public target, which the egress guard cannot stop (public destination). JWT secret forges tokens for any user incl. super admin; DB URL yields the database password; master key decrypts every org's stored secrets. The scan reproduced this end to end as the test admin and again as a freshly invited `user`-role member. On a deployment with open signup where this may already have been exercised, the leaked secrets need rotating — call that out to the operator, but it is **not** a step of this spec.

**Who legitimately uses `${env:}` today.** It is a documented self-hosted feature, paired with `${param:}` (org-managed, API-resolved, already safe):
- Docs: `web/docs/docs/cli.md:142,169`, `web/docs/docs/features/config-as-code.md:49`, `web/docs/docs/features/javascript-checks.md:93`, `web/docs/docs/features/check-types.md:100`; wiki `wiki/features/config-as-code.md:189-290`, `wiki/api-specification/checks.md:610-617`. Every secret-field JSON schema recommends it (`gen/checkerschema/build.go:33`, all `internal/checkers/schemas/*.json`).
- The stated model (`config-as-code.md:214-262`): `env:` is "the operator, on the process" — a self-hoster exports `SP_*` vars and references them; it "resolves on whichever process executes the check", with the deported-agent per-region-secret story. `envcheck.go:9-12` even exempts unknown `SP_*` names from its startup warning precisely because an operator may export arbitrary vars for `${env:}`.
- Tests exercising the happy path: `checkworker/secret_refs_e2e_test.go:137`, `checkworker/backend/ws_tunnel_test.go:234`, `integrations/sshtunnel/sshtunnel_test.go:568`, `handlers/checks/apply_test.go:306,432`, `handlers/checks/js_secrets_test.go:291`.

So the feature cannot simply be removed. The flaw is that **every** process env var is in scope and there is **no boundary** — exactly the hole `${param:}` was redesigned to close (namespace, not denylist: `resolvers.go:50-77`, `orgparams/service.go:8-22`).

## Proposal
Introduce an operator-controlled allowlist of env-var names that `${env:}` may resolve, enforced identically at save time and at resolve time. Default empty → `${env:}` resolves nothing (deny by default), matching how the egress guard and `param:` namespace are deny-by-default.

1. **Config knob.** Add an egress-style setting in `server/internal/config` (sibling to `EgressConfig`, `config.go:689-700`): `Checkers.EnvRefAllowlist []string` (koanf `checkers.env_ref_allowlist`) plus a manual env reader `SP_CHECK_ENV_ALLOWLIST` (comma-separated), read in `Load` alongside the other manual readers (`config.go:2266-2275`) because the koanf env loader collapses underscores. Expose a resolver, e.g. `Config.EnvRefAllowed(name string) bool`, that reports membership. Empty list ⇒ always false. Register the new `SP_*` name so `envcheck`/`RecognizedEnvVars` (`config/envvars.go:28-46`, `envcheck/envcheck.go:167-200`) recognizes it.
   - Keep the deported-agent story: an agent reads its OWN `checkers.*` config (see `worker.go:378-384`), so a private-region agent sets its own `SP_CHECK_ENV_ALLOWLIST` and the per-region-secret feature survives.
2. **Thread the allowlist predicate into the `secretref` resolvers.** `secretref` is a leaf package (`secretref.go:1-13`); do not import `config`. Give `LookupEnv` / the resolver constructors an injected `allow func(name string) bool`:
   - `ExecutionResolver` / `ExecutionResolverWith` (`resolvers.go:137-156`): resolving `SchemeEnv` first checks `allow(name)`; a disallowed name returns `Unresolvedf(SchemeEnv, name)` (same sentinel an unset var already yields) so the check goes visibly red with `unresolved secret reference: env:NAME`, never silently sending the literal.
   - `DocumentResolver` (`resolvers.go:96-111`): same gate, so import/apply refuses a disallowed `env:` with the existing `400 VALIDATION_ERROR` and the resolve-existence oracle closes.
   - Pass the predicate from each call site: the worker (`worker.go:944-945`, from `r.config.EnvRefAllowed`), the two tunnel paths (`ws_tunnel.go:50`, `sshtunnel.go:249`), and the write/validate paths (`apply.go:322`, which build `DocumentResolver(s.db, orgUID)`) from the checks service's `config`.
3. **Reject at write time, for the plain CRUD path too.** Add an `env:`-reference rule to `configValidationErrors` (`handlers/checks/validate.go:384-440`, next to `validateVarRefs` at `:405`), so create/update/clone/PUT and the dry-run validate endpoint all refuse a config whose `${env:NAME}` names a var outside the allowlist, with a `VALIDATION_ERROR` naming the key (reuse `secretref.VisitStrings` + `secretref.Pattern`, as `varrefs.go:17-39` and `apply.go:331-336` already do). This closes the gap that today only import/apply looks at `env:` at all — a plain `POST /checks` stores it unchecked.
4. **Keep one predicate, one grammar.** Route save-time and resolve-time through the same `secretref` helper so they cannot drift (the explicit design goal in `secretref.go:5-12`). A name allowed to save is exactly a name allowed to resolve.
5. **Migration-free note on existing stored configs.** No migration. Stored configs keep their `${env:NAME}` string verbatim (the reference is what is stored — `apply.go:276-289`). After this change, a stored reference outside the allowlist simply stops resolving: the check turns red with `unresolved secret reference: env:NAME` on its next run (same visible failure a deleted `param:` already produces, `config-as-code.md:294-301`), rather than leaking. An operator who was legitimately using `${env:}` adds the names to `SP_CHECK_ENV_ALLOWLIST` and the checks resolve again. Document this in `web/docs/docs/features/config-as-code.md` (the `env:` section at `:257-262`) and `wiki/features/config-as-code.md:257-262`.

## Tests
- `server/internal/secretref/secretref_test.go` (table-driven): extend `TestExecutionResolverRefusesParam`'s neighborhood with cases proving `ExecutionResolver` with an `allow` predicate (a) **regression**: resolves a name that was in scope before, now returns `ErrUnresolved` when the name is not allowlisted — fails before the fix (today it resolves); (b) **positive control**: an allowlisted name still resolves to its value; (c) a `${param:}`/`${var:}` reference is unaffected.
- `server/internal/secretref/secretref_test.go`: a `DocumentResolver` case proving a disallowed `env:` yields `ErrUnresolved` (closing the import/apply existence oracle) and an allowlisted one resolves.
- `server/internal/handlers/checks/validate_test.go` (or the existing config-validation test file): **regression** — creating/patching a check whose config holds `${env:SOME_SECRET}` outside the allowlist returns `VALIDATION_ERROR`; **positive control** — an allowlisted name passes, and a config with no `env:` ref is unaffected. Run through the real create path so it also covers clone/PUT/MCP (shared `firstConfigValidationError`).
- `server/internal/checkworker/secret_refs_e2e_test.go`: update `TestWorkerResolvesEnvReferenceOnTheExecutingProcess` to set the allowlist for its fixture var (positive control, the legitimate flow still works end to end) and add a **regression** case where the fixture var is NOT allowlisted and the job produces a `status: error` result carrying `unresolved secret reference: env:…` — not the secret.
- `server/internal/config/envvars_test.go` / `envcheck_test.go`: `SP_CHECK_ENV_ALLOWLIST` is recognized (no spurious unknown-var warning) and parses comma-separated values.

## To verify
- Exact field placement: whether to hang the allowlist off `CheckersConfig` (`config.go:342-351`, already single-word-key-sensitive for the koanf env quirk) or a new `secretref`/`checks` config block. `CheckersConfig` is the natural home but its keys must stay single-word or get a manual reader — `env_ref_allowlist` needs the manual `SP_CHECK_ENV_ALLOWLIST` reader either way.
- That no other code path resolves `${env:}` outside the four resolver call sites found (grep for `ExecutionResolver`/`DocumentResolver`/`LookupEnv` returned only worker.go, the two tunnel files, apply.go, and the secretref package itself).

## Open questions
1. **Design: allowlist vs. prefix vs. disable-for-org-authored.** Recommended: an explicit operator allowlist of names (`SP_CHECK_ENV_ALLOWLIST`), empty by default. It is the least surprising for the documented self-hosted use (operators already name the vars they export), survives the deported-agent per-region story (each agent sets its own), and is a true boundary rather than a denylist. A fixed `SP_CHECK_ENV_*` prefix was considered but would force self-hosters to rename existing vars; "disable `env:` for org-authored configs" cannot be expressed cleanly because the worker has no org identity at resolve time (`worker.go:375-377`).
2. **Default on upgrade.** Empty allowlist means every existing `${env:}` reference stops resolving until the operator lists the names. Recommended: ship empty (secure default) and call it out prominently in the changelog + upgrade note, since the alternative (grandfather existing names) would require reading every stored config and would re-open the oracle for those names. Self-hosters relying on `env:` set one env var to restore it.
